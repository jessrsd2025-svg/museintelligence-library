Integrated Analytical Environment
Renderings of Strategic Dynamics defines a conceptual analytical environment that brings together geospatial observations, infrastructure data, documentary evidence, and graph relationships within a provenance-aware knowledge fabric.
The framework supports transparent, explainable analysis through standardized data transformation, cryptographic lineage, and human-centered review. Cartography is treated not only as a representation of places, but also as a representation of evidence: analysts can trace how observations become relationships, how those relationships support knowledge, and how each assessment remains linked to documented sources.
Multi-Agent Consensus Model
Decision-making is structured as a controlled contest among specialized agents. Each agent examines a proposed action from a distinct analytical, operational, or governance perspective before the system advances toward consensus.
Proposer Agents: Generate candidate plans for evaluation.
Critic Agents: Identify risks, gaps, assumptions, and likely failure modes.
Policy Agents: Check proposed actions against applicable constraints.
Security Agents: Evaluate authorization, access conditions, and operational safeguards.
Provenance Agents: Validate lineage, source attribution, and traceability.
Cost/Lag Agents: Assess efficiency, resource cost, and latency.
Human Review Agents: Escalate high-risk or uncertain actions for analyst oversight.
Consensus Engine: Selects, rejects, or returns plans for revision.
Consensus Flow
Structured Context → Candidate Plans → Critic Review → Policy Validation → Security Validation → Provenance Validation → Consensus → Human Interrupt → Validated Intent

# Proposer Agent

## Mission

Generate bounded candidate plans from a structured orientation package.

The Proposer Agent does not approve or execute actions.

## Inputs

- Observation identifiers
- Orientation package
- Resolved entities and locations
- Graph relationships
- Evidence-chain references
- Confidence values
- Policy constraints
- Mission objective
- Time and resource constraints

## Required outputs

- Candidate plan identifier
- Plan objective
- Evidence used
- Assumptions
- Expected effects
- Reversibility
- Dependencies
- Risk estimate
- Confidence estimate
- Human-review requirement

## Guardrails

- Do not convert proximity into attribution.
- Do not treat a report as verified evidence.
- Do not conceal assumptions.
- Do not recommend action unsupported by provenance.
- Do not generate kinetic targeting recommendations.
- Mark incomplete plans `INSUFFICIENT_EVIDENCE`.

## Corridor assignment

Develop a provenance-aware analytical model connecting the Strait of Hormuz,
Gulf of Oman, Arabian Sea, Gulf of Aden, Bab el-Mandeb, Red Sea, and Suez Canal.

Each event should be represented as:

```text
Observation
→ GeoFeature
→ RFC 8785 canonical object
→ SHA-256 digest
→ Evidence-chain node
→ GraphRAG retrieval object
→ Human review
````

## Mission

Challenge candidate plans, source interpretations, confidence values, causal
assumptions, and graph relationships.

## Required tests

- Alternative-hypothesis test
- Source-independence test
- Temporal-consistency test
- Spatial-validity test
- Attribution test
- Provenance-completeness test
- Policy-conflict test
- Feedback-loop test
- Commercial-activity ambiguity test

## Corridor risk questions

- Is the activity unusual relative to baseline commercial traffic?
- Are sources genuinely independent?
- Is actor attribution direct, inferred, or merely alleged?
- Could the observation represent legitimate dual-use activity?
- Are time references sufficiently precise?
- Is spatial proximity being confused with organizational association?
- Are chokepoint conditions creating collection bias?
- Is the graph amplifying a claim repeated by dependent sources?

- [ ] Canonicalization status is recorded.

- [ ] Source dependence is evaluated.
- [ ] Transformation history is retained.
- [ ] Confidence is distinct from source reliability.
- [ ] Human review status is explicit.

lineage_status: COMPLETE | PARTIAL | BROKEN

- Serverless functions
- Database transaction workers

> This conceptual model is limited to authorized analytical, administrative, data
> processing, and reporting functions. It does not authorize kinetic action,
> intrusive collection, targeting, unauthorized access, or autonomous enforcement.

## Governing rule

> No action executes without validated intent, recorded constraints, an execution
> identifier, and a defined rollback or termination condition.

## Execution flow

```mermaid
flowchart LR

    SP --> FB[Feedback and Re-observation]

## Preconditions


Before execution, the system validates:


- `validated_intent_id` exists.
- Decision record exists.
- Approved plan identifier matches the decision.
- Evidence-chain references resolve.
- Policy constraints pass.
- Security constraints pass.
- Human approval exists when required.
- Requested tool is authorized.
- Inputs conform to schema.
- Idempotency key is present.
- Timeout is defined.
- Rollback or safe termination is available.
- Execution scope has not expired.

- Allowlisted endpoints
- Least-privilege credentials
- Schema-validated requests
- Rate limits
- Timeouts
- Idempotency controls
- Response validation
- Redacted audit logging


Secrets must not be written into Obsidian notes, prompts, execution records, or
retrieval chunks.

## Execution result states


| State | Meaning |
| --- | --- |
| `PENDING` | Execution record created |
| `VALIDATING` | Preconditions are being tested |
| `BLOCKED` | One or more mandatory gates failed |
| `DRY_RUN_COMPLETE` | Simulation completed without external change |
| `AWAITING_HUMAN_REVIEW` | Analyst authorization is required |
| `AUTHORIZED` | Execution is approved within defined scope |
| `EXECUTING` | Bounded action is in progress |
| `COMPLETED` | Action completed and output was recorded |
| `FAILED` | Action failed before successful completion |
| `ROLLING_BACK` | Compensating operation is in progress |
| `ROLLED_BACK` | Previous state was restored or mitigated |
| `FEEDBACK_REGISTERED` | Effects were sent to the observation layer |


## Failure handling


### Authorization failure


- Stop execution.
- Record failed control.
- Preserve the request.
- Notify the human-review queue.
- Do not retry automatically.


### Schema failure


- Reject malformed input.
- Record validation errors.
- Return the plan to the proposing workflow.
- Do not infer missing sensitive parameters.


### Tool failure


- Stop or isolate the action.
- Capture tool output and error state.
- Initiate rollback when safe.
- Register a feedback observation.


### Provenance failure


- Block execution.
- Mark the chain `BROKEN` or `PARTIAL`.
- Return to [[Observe_Event_Ingestion]] or [[Orient_GraphRAG_Context]].
- Require analyst review before reactivation.


### Unexpected state change


- Associate the state change with the execution identifier.
- Prevent it from entering the graph as an unrelated external event.
- Invoke [[Feedback_State_Probing]].
- Escalate when impact exceeds the approved envelope.


## Feedback requirement


Every completed, failed, or rolled-back action emits a feedback event:


```
feedback_id:execution_id:observed_at:expected_effects: []observed_effects: []unexpected_effects: []state_before_digest:state_after_digest:impact_level:requires_reorientation:requires_human_review:
```


## Success criteria


The `ACT` phase is complete only when:


- Execution status is terminal.
- Action hash is recorded.
- Result digest is recorded.
- Audit log is complete.
- Rollback state is recorded.
- Human review is linked when required.
- State probe has run.
- Feedback has entered re-observation.
- Side effects are associated with the originating execution.
