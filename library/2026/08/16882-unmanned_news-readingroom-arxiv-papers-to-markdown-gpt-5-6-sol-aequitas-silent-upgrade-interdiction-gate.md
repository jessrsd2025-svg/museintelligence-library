# AEQUITAS Silent-Upgrade Interdiction Gate


The AEQUITAS Gate is the mandatory boundary between **analytical reasoning** and **persistent knowledge mutation**. Its central invariant is:


> Multi-agent agreement may improve analysis, but consensus does not establish truth.


A crucial refinement to the doctrine is therefore:


```
Observations  → Features  → Proposed Relationships  → Evidence and Policy Adjudication  → Human-Approved Relationships  → Governed Knowledge
```


Features and relationships do **not** automatically become verified knowledge.


## Governance precedence


```
Human-Approved Policy  > AGENTS.md  > AEQUITAS Gate  > Task Contract  > CHAIN.md Dispatch  > Model Preference
```


Lower-precedence components cannot override higher-precedence controls:


- `CHAIN.md` selects a reasoning mode; it does not authorize a mutation.
- A task contract defines expected work; it cannot bypass prohibited-edge policy.
- `AGENTS.md` defines repository permissions and epistemic boundaries.
- AEQUITAS deterministically evaluates every proposed promotion or relationship.
- Human approval is required for sensitive epistemic or graph transitions.


---


## 1. What constitutes a silent upgrade?


A silent upgrade occurs when a system changes the meaning or certainty of information without an explicit, authorized transition record.


| Input | Prohibited silent upgrade |
| --- | --- |
| Source assertion | Verified fact |
| Entity mention | Resolved identity |
| Spatial proximity | Operational presence |
| Thematic similarity | Corroboration |
| Model score | Evidence confidence |
| Influence claim | Command relationship |
| Financial association | Financing attribution |
| Scenario date | Observed event |
| Generated map | Source geography |
| Multi-agent consensus | Independent verification |


The gate must inspect both **relationship types** and **property changes**. Blocking `CONTROLS` while allowing an agent to set `claim_status = VERIFIED` would leave an equally serious bypass.

The default behavior is **fail closed**. Missing provenance, an unknown relationship class, malformed review records, or ambiguous policy produces quarantine—not approval.

## 3. Relationship disposition


### Prohibited automatic relationships


```
CONTROLSDIRECTSOWNSOPERATES_INRESPONSIBLE_FORTARGETSCOMMANDSFINANCESEXECUTES_C2DIRECTS_CAMPAIGN
```


These relationships may be represented only as unverified propositions in the adjudication queue. They are not automatically rewritten into weaker graph facts.


### Allowed evidence-centered relationships


```
SOURCE_ASSERTS_CLAIMCLAIM_MENTIONS_ENTITYCLAIM_RELATED_TO_GEOFEATURESUPPORTED_BYCONTRADICTED_BYREQUIRES_REVIEWRELATED_TORESOLVES_TOSHARES_REGISTRAR_WITHTHEMATICALLY_SIMILAR_TO
```


Even an allowed relationship still requires provenance and schema validation.


### Safe disposition model


```

```


For ambiguous, non-causal relationships, the gate may suggest `RELATED_TO`. That downgrade must remain explicit:


```
original_relationship: ENABLES_ACTIVITYeffective_relationship: RELATED_TOdisposition: DOWNGRADED_PENDING_REVIEWoriginal_semantics_preserved_in_audit: true
```


The original proposal must never be erased from the audit record.

## 4. Epistemic transition control


Claim type and claim status must remain separate.


```
claim_type: SOURCE_ASSERTIONclaim_status: UNVERIFIEDsource_id: SRC-REUTERS-EXAMPLEattribution_form: ALLEGED_BY_SOURCE
```


A valid promotion requires an explicit transition object:


```
transition_id: EPI-TRANSITION-001claim_id: CLAIM-IRGC-OIL-001from_status: UNVERIFIEDto_status: PARTIALLY_CORROBORATEDrequested_by: PROVENANCE_REVIEWERevidence_added:  - EVIDENCE-PRIMARY-001  - EVIDENCE-INDEPENDENT-002policy_result: PASShuman_disposition_id: HR-2026-001effective_at: null
```


AEQUITAS rejects the transition if:


- `from_status` does not match the current database state;
- evidence records lack source locators;
- sources are not independent;
- the reviewer is unauthorized;
- the human disposition applies to another claim or artifact;
- the transition attempts to promote model output directly;
- required dissent or contradiction records were omitted.


Model scores remain distinct:


```
value: 0.87value_type: MODEL_SCOREis_evidence_confidence: falseis_corroboration: falseallowed_for_epistemic_promotion: false
```

## 5. Multi-agent consensus safeguards


The review mesh should produce **independent signed dispositions**, not a single blended answer.


| Reviewer | Governing question |
| --- | --- |
| Planner | Is the task decomposed correctly? |
| Critic | What assumptions or contradictions remain? |
| Provenance Reviewer | Are source identity, locator, lineage, and independence adequate? |
| Policy Reviewer | Is the proposed transition permitted? |
| Security Reviewer | Does it expand permissions, exposure, or mutation scope? |
| Human Reviewer | Is the exact transition authorized? |


An example decision envelope:


```
{  "proposal_id": "PR-2026-08-05-001",  "reviews": [    {      "role": "PLANNER",      "result": "PASS",      "scope": "task-completeness"    },    {      "role": "CRITIC",      "result": "DISSENT",      "scope": "unsupported-causality"    },    {      "role": "PROVENANCE_REVIEWER",      "result": "FAIL",      "scope": "independent-corroboration"    },    {      "role": "POLICY_REVIEWER",      "result": "BLOCK",      "scope": "prohibited-edge"    }  ],  "aggregate_result": "QUARANTINED",  "consensus_is_verification": false}
```


A majority vote cannot override a policy block. Dissent must be preserved and passed through the Context Gate rather than summarized away.


---


Models and reasoning agents should never receive direct Neo4j write credentials. They submit proposals to D1 or another append-only adjudication service.


```
Agents  → Proposal API  → D1 proposed_relationships  → AEQUITAS evaluation  → Human disposition  → Restricted mutation worker  → Neo4j
```


Only the restricted mutation worker may execute graph writes. It should require:


- an approved disposition;
- an unexpired authorization;
- an exact proposal hash;
- a policy-version identifier;
- optimistic concurrency controls;
- an idempotency key;
- rollback metadata.


Illustrative approved mutation:


```
MATCH (a {node_id: $fromNode})MATCH (b {node_id: $toNode})MATCH (d:HumanDisposition {  disposition_id: $dispositionId,  disposition: 'APPROVED'})WHERE d.proposal_hash = $proposalHash  AND d.policy_version = $policyVersionMERGE (a)-[r:RELATED_TO {  proposal_id: $proposalId}]->(b)ON CREATE SET  r.created_at = datetime(),  r.disposition_id = d.disposition_id,  r.policy_version = d.policy_version,  r.epistemic_status = 'HUMAN_APPROVED_RELATIONSHIP',  r.allowed_for_automated_action = falseRETURN r;
```


The relationship type should come from a server-side allowlist. It must not be interpolated directly from model-generated text.


Prohibited proposals remain first-class nodes or records rather than executable relationships:


```
CREATE (p:RelationshipProposal {  proposal_id: $proposalId,  proposed_type: 'CONTROLS',  disposition: 'QUARANTINED',  graph_mutation_authorized: false,  human_review_required: true});
```

```
type GateResult =  | { result: 'ALLOW'; effectiveRelationship: string }  | { result: 'QUARANTINE'; reason: string }  | { result: 'REJECT'; reason: string };function evaluateProposal(proposal: Proposal, context: Context): GateResult {  if (!context.schemaValid) {    return {      result: 'REJECT',      reason: 'SCHEMA_VALIDATION_FAILED',    };  }  if (!proposal.sourceId || !proposal.sourceLocator) {    return {      result: 'QUARANTINE',      reason: 'INCOMPLETE_PROVENANCE',    };  }  if (context.prohibitedEdges.has(proposal.relationship)) {    return {      result: 'QUARANTINE',      reason: 'PROHIBITED_CAUSAL_EDGE',    };  }  if (proposal.requestsEpistemicPromotion) {    if (!proposal.transitionRecord) {      return {        result: 'QUARANTINE',        reason: 'SILENT_EPISTEMIC_UPGRADE',      };    }    if (!context.validHumanDisposition) {      return {        result: 'QUARANTINE',        reason: 'HUMAN_DISPOSITION_REQUIRED',      };    }  }  if (proposal.derivedFromSemanticSimilarity) {    return {      result: 'QUARANTINE',      reason: 'SIMILARITY_IS_NOT_CORROBORATION',    };  }  if (proposal.derivedFromSpatialProximity) {    return {      result: 'QUARANTINE',      reason: 'PROXIMITY_IS_NOT_OPERATIONAL_PRESENCE',    };  }  if (!context.allowedEdges.has(proposal.relationship)) {    return {      result: 'QUARANTINE',      reason: 'UNKNOWN_RELATIONSHIP_CLASS',    };  }  return {    result: 'ALLOW',    effectiveRelationship: proposal.relationship,  };}
```


## Required invariants


```
aequitas_invariants:  default_disposition: QUARANTINE  consensus_is_verification: false  semantic_similarity_is_evidence: false  spatial_proximity_is_presence: false  model_score_is_evidence_confidence: false  generated_geometry_is_source_geography: false  scenario_anchor_is_observation: false  direct_agent_graph_credentials: prohibited  prohibited_edge_auto_creation: prohibited  human_approval_scope_must_match: true  dissent_preservation_required: true  audit_record_immutable: true
```


This makes AEQUITAS more than an edge-name filter: it becomes a transactional firewall governing **provenance, epistemic transitions, entity resolution, spatial meaning, authorization, and graph mutation**.


***Binding to a Unified Intelligence Lattice***


To make these mindsets collaborative, the architecture binds these cognitive transitions to persistent repository instructions (**AGENTS.md**), contract-driven verification harnesses, and a **Neo4j Property Graph Engine**.


This ensures that the outputs of these various mindsets are systematically structured: **observations** are logged as features, features are mapped into **relationships**, and those relationships ultimately build verified **knowledge**. By passing reasoning through this multi-agent consensus mesh (comprising Planners, Critics, Provenance Reviewers, and Policy Reviewers), the system achieves non-linear OODA decision loops while strictly preventing hallucinated causality or unverified promotions of facts.


Ultimately, the architecture operates under a strict governance precedence hierarchy where mathematical and human-approved policies safely constrain these synergistic cognitive engines: **Human Policy Approval > AGENTS.md > AEQUITAS Gate > Task Contract > CHAIN.md Dispatch > Model Preference**.
